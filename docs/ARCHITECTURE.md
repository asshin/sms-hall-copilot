# HarborTel 短厅 Copilot · 与现网短厅的对照

本作品复用的是**业务模式**，不是现网代码。虚构运营商 HarborTel，短码 1880。

## 现网链路（CMHK 短厅，概念层）

```
用户短信 → smgw 网关 → see 业务引擎（指令匹配 / 会话）
        → ussdweb 办理（调 CRM/BCOC）
        → mnp 消息中心下行
配置在 busims / 维护工作台 / 隐性指令表
```

生产里必须处理：精确指令、多轮 2way、Y 确认、预付/后付差异、70/160 字、失败码映射、流控与审计。

## 作品链路

```
MO 短信 → matcher 规则（BAL/菜单数字/Y|N）
        → 未命中则 RAG + 意图 JSON（LLM 或启发式）
        → policy 套餐与状态门
        → 敏感意图只挂起，等确认
        → tools Mock BSS
        → SMS composer（UCS-2 70 / GSM 160）
        → trace（路由、工具、时延、token）
```

配置助手两条：① 自然语言需求 → 已有意图的指令草案；② 接口描述 + 出入参 → 新意图（只落 Mock 合同，不调真实 CRM）。均须人工确认后写入。

## 有意不做的设计

| 不做 | 原因 |
|------|------|
| 短厅主路径上的自由 Agent | 动作空间封闭，Agent 增加不可审计的办理 |
| 用模型生成余额/成功文案 | 办理结果必须来自工具 |
| 接入真实 CRM | 作品与现网隔离 |
| LangChain 重封装 | 面试要讲清自己的状态机，而不是框架 |

## 你要能讲的三个决策

1. **规则优先**：精确指令 100% 不走模型，避免把 `BAL` 理解成闲聊。
2. **确认门在引擎，不在 Prompt**：用户说「不要确认直接停」仍然 `confirm_required=true`。
3. **评测是产品的一部分**：没有 golden set 的 Demo 只是玩具。
